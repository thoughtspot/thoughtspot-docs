== New features and functionality

The latest release of ThoughtSpot Cloud contains several new and enhanced features.

The features described in these release notes may have one of the following statuses.

[.borderless,width=88%]
|===
|Feature statuses

|[.badge.badge-beta-relnotes]#Beta#

Beta features are incomplete and may change before GA. They are enabled for select customers to collect feedback and have limited documentation. Beta features are disabled by default. Your administrator must contact {support-url} to enable them.

|[.badge.badge-early-access-relnotes]#Early Access#

Early Access features are complete and supported, but not yet enabled by default. You can try them before GA, with full documentation available. Early Access features are disabled by default. Refer to the feature documentation for how to enable them.

|[.badge.badge-ga-relnotes]#GA#

General Availability (GA) features are usually enabled by default for all customers. They are fully supported. If the GA feature is not enabled by default, the process for enabling it is noted in the documentation.
|===

#Monitor Spotter usage and conversations# [.badge.badge-ga-relnotes]#GA#::
// Mary. jira: SCAL-338336. docs jira: SCAL-338337
// PM: Mayur. is this a new Spotter Liveboard? How does it differ from the Spotter conversations Liveboard? where is the Spotter settings menu? add image/ video. shorten blurb
Administrators can now monitor Spotter usage across their Org directly from Spotter > Settings. *Monitor all chats* opens a searchable, filterable list of every Spotter conversation in the Org, with each chat readable in full read-only view including Spotter's reasoning. Spotter metrics provides a Liveboard of aggregate usage data including feedback scores and response latency, giving administrators visibility into adoption trends and answer quality over time. Monitoring is scoped to the signed-in Org in multi-Org instances and is available in the Liveboard side panel (New) experience of Spotter 3.

#New privileges to control content creation and analysis# [.badge.badge-ga-relnotes]#GA#::
// Mary. jira: SCAL-331949. docs jira: SCAL-331950
// PM: Siddhant. switch bullet list to a table and explain more. change first line to summarize rbac-- can administer schedules privilege is not related to "creating content and analyzing data"
Administrators can now use roles to control who can create content and analyze data. These new privileges are available on instances with Roles enabled:

* *Can create Liveboards*: Create, edit, copy, pin to, and delete Liveboards.
* *Can create Answers*: Search data, and create, edit, and save Answers.
* *Can analyze data*: Use Explore, Drill down, Change analysis, and Show underlying data.
* *Can administer schedules*: Manage all schedules in the Org.
+
All existing and new users have the first three privileges by default, so nothing changes until an administrator revokes a privilege for a group. When a privilege is revoked, the related actions are hidden for those users. All users can still view Liveboards and Answers.

#Manage formula variables in secondary Orgs# [.badge.badge-ga-relnotes]#GA#::
// Mary.  jira: SCAL-293363. docs jira: SCAL-293364 & jira: SCAL-312203. docs jira: SCAL-312204
// PM: Sejal. image. see if you can merge with Variables UI in secondary orgs
Variables now support several enhancements in the Admin portal. Formula variables can be assigned a data type (such as string, integer, date, or boolean) at creation, ensuring values are validated against the target column type and resolve correctly in RLS rules and formulas without conversion wrappers. Variable values can now be scoped to individual users and groups in addition to Orgs, with values resolved at query time in user > group > Org > default order. A default value can also be set on a variable, used as a fallback when no scoped value matches the current user context, preventing query failures for users or Orgs without an explicitly assigned value.
+
Additionally, Org administrators and users with *Can manage variables* privileges can now create and manage formula variables from the Variables page in their own Org, without switching to the primary Org. This includes assigning values scoped to that Org for use in RLS rules.

#Column security rules: Attribute-based access control and publishing# [.badge.badge-ga-relnotes]#GA#::
// Mary. jira: SCAL-311897. docs jira: SCAL-312204
// PM: Sejal. add an example. How is this different from column-level security?
Column security rules now support attribute-based access control (ABAC), letting administrators express column visibility as a boolean rule over user attributes rather than by group membership. Existing group-based column security requires a separate group for every combination of access dimensions (role, region, tier, and so on), which becomes unmanageable at scale and cannot be applied across Orgs. ABAC rules evaluate against the attributes the user already carries from their identity system, so a single rule covers all combinations and a primary-Org admin can publish a rule that is enforced across all secondary Orgs automatically. Rules are authored in the formula editor, supported in TML and the REST API v2, and enforced everywhere column security applies: tables, Models, Answers, Liveboards, Search, and Spotter. Group-based rules continue to work unchanged alongside them.
