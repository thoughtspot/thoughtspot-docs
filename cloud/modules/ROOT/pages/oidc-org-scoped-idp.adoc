= Org-scoped IdP connections and login page rendering
:page-last_updated: Aug 31, 2026
:author: Mary, Rani
:linkattrs:
:experimental:
:page-layout: default-cloud-beta
:description: Learn how Org-ccoped IdP connections and login page rendering works.

NOTE: This feature is currently in Beta. Some behaviors and UI controls may change before general availability. To enable this feature, contact {support-url}.

Org-scoped IdP connections give each Org in your ThoughtSpot cluster its own isolated authentication configuration. The login page renders only the IdP connections that belong to that Org. Connections from other Orgs have no effect.

NOTE: #See <<Prerequisites>> for details on per-org subdomain and how it affects login page behavior.#

Previously, IdP connections were evaluated cluster-wide at login time. If any Org in the cluster had an IdP connection configured, ThoughtSpot's login page would automatically trigger an IdP discovery redirect, regardless of which Org the user was trying to reach.

This caused two significant problems:

* *First-time login failures* +
Okta and similar IdPs only allow SSO login after a user has previously completed an IdP-initiated flow.
New users were redirected into a flow they couldn't complete, effectively blocking access.

* *Cross-Org interference* +
Adding an IdP connection in one Org could unintentionally change the login experience for another Org, even though the two Orgs are independent.

Org-scoped IdP connections eliminate both issues.

== #Prerequisites#

Before enabling org-scoped IdP connections, note the following requirements:

// SOURCE: SCAL-334079 (Swarnima Dora, 2026-08-28)
* *IAMv2 must be enabled on the cluster.* +
Org-scoped IdP connections are supported only on IAMv2-enabled clusters with orgs enabled.

* *Per-org subdomain must be enabled for org-level login page isolation.* +
The org-scoped IdP feature works in two modes depending on whether per-org subdomain is enabled on your cluster:
+
** *Per-org subdomain disabled:* The cluster login page renders the Primary org's IdP connections only. Non-primary orgs do not get a dedicated login page.
** *Per-org subdomain enabled:* Each org's subdomain URL (for example, `\https://<org-name>.<cluster-name>.thoughtspot.cloud`) renders only that org's IdP connections. The shared cluster URL continues to render the Primary org's IdP connections.

To enable Per-org subdomain, open a Salesforce support ticket requesting *Per Org Subdomain* or contact {support-url}. For details, see xref:multi-idp-behavior.adoc#_multiple_idps_with_the_per_org_subdomain_configured[Multiple IdPs with the per Org subdomain configured].

== How it works

With this feature enabled, the login page is rendered based exclusively on the IdP connections configured for that Org.

[cols="1,2",options="header"]
|===
|IdP connections in the Org |Login page behavior

|None
|Standard username/password login

|One
|That IdP connection is displayed directly

|More than one
|Controlled by admin configuration
|===

NOTE: #When per-org subdomain is enabled, IdP connections from other orgs are never evaluated or rendered on an org's subdomain login page. When per-org subdomain is disabled, the cluster login page always renders the Primary org's IdP connections, regardless of which org the user intends to reach.#

The automatic IdP discovery redirect is disabled as part of this change.
ThoughtSpot no longer auto-redirects users based on cluster-wide IdP detection.

=== Configuring Org-scoped IdP connections

To enable this feature, contact {support-url}.

. Navigate to *Admin settings*.
. Click *Security* and select *SSO configuration* for the Org.
+
Two controls are available:

* *Show all IdP connections*
+
Toggle on to display all IdP connections configured for the org on the login page. Toggle off to show only the default connection.
* *Default IdP connection*
+
Select which connection is treated as the default. This is the connection shown when *Show all* is off.

== Limitations

* UX for multi-connection selection on the login page is subject to refinement before general availability.
* Validation tooling for detecting misconfigured Org IdP setups is not yet available.
