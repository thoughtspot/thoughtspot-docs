== Overview

The Admin settings portal has been completely redesigned, to be a more intuitive, and highly organized administrative experience tailored for modern ThoughtSpot administrators.
It consolidates governance and provides administrators with unprecedented control and visibility, serving as the foundation for the next generation of enterprise scale.

The redesigned portal solves the problem of a cluttered and fragmented administrative interface by introducing a unified Information Architecture (IA) that brings closely related items together to create a streamlined, logical workflow.

NOTE: The redesigned Admin settings portal is rolling out in phases. Your cluster will be upgraded during the 26.8.0.cl release, with some customers receiving access earlier than others to facilitate real-world testing.


== What's New?

The new Admin settings portal include the following key changes:

* A new information architecture. The new architecture consists of four primary sections:
** Home
** Management
** Configuration
** Monitor
* A new interface for Application Settings
* An improved workflow to Create, Read, Update, and Delete (CRUD) Orgs
* An improved interface and workflow to Create, Read, Update, and Delete (CRUD) Users

These are all accessible from a streamlined navigation sidebar.

== User roles and permissions

Admin settings support the following administrative roles:

[cols="1,3", options="header"]
|===
| Role | Description

| ThoughtSpot Administrators
| Full administrative access to all ThoughtSpot functionality, including cluster-level and org-level settings.

| Cluster admins
| Responsible for overarching settings and *allocating features* to Orgs.
Cluster admins control which features are available for delegation to individual Org.

| Org admins
| Responsible for managing their specific organization environment.
Org admins can *toggle allocated features* within their org but cannot access features that have not been allocated to them by a cluster admin.

| Users
| Standard users with no administrative access.
They interact with ThoughtSpot through Search, Liveboards, and Answers but cannot access the Admin settings portal.
|===


For Org admins to toggle a feature, the cluster admin must first allocate that feature to the Org.
If a feature is not allocated, the Org inherits the cluster-level setting.

== Feature Management

Feature Management in the enhanced Admin settings portal introduces a *granular, hierarchical system* that transitions from cluster-level configurations to delegated authority at the org level.

=== Two-tiered hierarchy

The feature management system operates on a two-tiered model:

. *Cluster admin allocates a feature:* The cluster admin must first allocate a feature to an Org.
Once allocated, the Org admin gains authority to toggle that feature on or off within their organization.

. *Org inherits cluster-level setting:* If a feature is not allocated to an Org, the Org simply inherits the cluster-level setting.
The Org admin cannot modify features that have not been allocated to them.

[cols="2,3", options="header"]
|===
| Tier | Responsibility

| Tier 1: Cluster admin
| Allocates features to orgs.
Controls which features are available for delegation.
Sets cluster-level defaults.

| Tier 2: Org admin
| Toggles allocated features on or off within their organization.
Cannot access unallocated features.
|===

=== Global setting overrides

When a cluster admin enables a feature globally, they are prompted to choose:

* *Override all orgs:* Apply the new setting across all organizations, replacing any local overrides.
* *Preserve local overrides:* Keep the choices made by individual Org admins where applicable.

[TIP]
====
Cluster admins should preserve local overrides when changing a global setting to maintain the choices made by individual Org admins, where appropriate.
This respects the autonomy of org-level administrators and avoids unintended disruptions.
====

== Best practices

* Use the *secure deletion workflow* (typing a confirmation word) to prevent accidental, destructive deletions of organizations.
* Cluster admins should *preserve local overrides* when changing a global setting to maintain choices made by individual Org admins, where appropriate.
* Consolidate branding and style management into the single *Customisation* tab to maintain a single source of truth for your organization's visual identity.

== Frequently asked questions

=== How does the hierarchy work for feature flags?

The system is two-tiered.
The cluster admin must first "allocate" a feature to an Org.
Once allocated, the Org admin gains authority to toggle it.
If not allocated, the Org simply inherits the cluster-level setting.

=== What happens if a cluster admin changes a global setting?

When enabling a feature, the cluster admin is prompted to choose whether to override all orgs or preserve local overrides (keeping the choices made by individual Org admins).
