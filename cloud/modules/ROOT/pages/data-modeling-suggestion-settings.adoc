We have added the *Suggestion settings* column to Models to allow you to control the data that appears in typeahead suggestions and column knowledge cards, and the data used to improve Spotter accuracy. Previously, #on Models with underlying tables having row-level security defined#, you may have seen suggested names of data that you could not access in typeahead suggestions or in column knowledge cards. This occurs only when you define the RLS rule on a different table than the one that contains the column you want to restrict.

For example, if you only had access to data in California, you could see that data for Texas existed, although you could not access it. Now, you can restrict suggested data for Models with row-level security, ensuring that your security is complete.

[NOTE]
====
#All metadata queries for a model column set to *Secure suggestions* run against your primary warehouse or cloud data warehouse (CDW). ThoughtSpot cannot route these queries to a secondary warehouse configured for background indexing workloads. For more information, see <<secondary-warehouse,Secondary warehouse and secure suggestions>>#.
====

== #How secure suggestions works#

When a model column is configured with *Secure suggestions*, ThoughtSpot cannot pre-index its values because each user may be entitled to see a different subset of values under row-level security. Instead, ThoughtSpot fetches a small sample of values live from the warehouse the first time a user's search or Spotter session needs them, then caches the result for 24 hours.

These on-demand queries appear in your warehouse query history tagged as `SECURE_SAMPLING` (for sample values) and `SECURE_MATCH_VALUES` (for Spotter suggestion matching).


=== #Query volume and caching#

ThoughtSpot fetches values from the warehouse only when a search or Spotter session needs them, then caches the result for 24 hours. Because the fetch happens on demand rather than during scheduled indexing, enabling *Secure suggestions* on more model columns increases the number of queries your primary warehouse receives.

A `SECURE_SAMPLING` query typically takes around 60 seconds to run, so the first search that needs values for a model column may see a short delay before suggestions appear.

If the query fails, ThoughtSpot temporarily suppresses that model column's suggestions and retries after a backoff period. Suggestions recover automatically once the warehouse responds successfully.

=== #When to use secure suggestions#

Enable *Secure suggestions* for a model column when any of the following apply:

* Row-level security is applied to the underlying tables and you need typeahead suggestions or sample values to honor that security.
* RLS rules use constructs that the standard search index cannot enforce, such as `and`, `ts_var`, or `!=`.
* Spotter accuracy matters on RLS-protected Models and suggestions must be strictly RLS-compliant.
* The underlying table column has no index but you still want sample values or suggestions in knowledge cards.
* ThoughtSpot displays a potential data-leak warning when the Model has RLS defined but model columns are set to *Inherit table settings*.

=== #When not to use secure suggestions#

Do not enable *Secure suggestions* when:

* No row-level security is applied to the underlying tables.
* You plan to enable it on every model column of a Model without evaluating each model column's security requirements. Enabling it indiscriminately generates unnecessary warehouse queries.
* Suggestions are not needed for the model column at all. Use *Don't show suggestions* instead.

[IMPORTANT]
====
Enabling *Secure suggestions* on model columns that do not require it increases query load on your primary warehouse. Set this option only on model columns where row-level security compliance for suggestions is required.
====

== Set secure suggestions

You can set the suggestion settings on any #model column#, and specify to not show suggestions, inherit table settings, or use secure suggestions.

[.bordered]
image::secure-suggestions.png[Secure suggestions option in the Suggestion settings column.]

#When you set a model column to *Inherit table settings*, the model column takes the suggestion security setting defined on its source table, and that setting applies everywhere the values are used, not only in typeahead suggestions and column knowledge cards. The data is secure only when the row-level security rule is defined on the same table that contains the referenced column. If the rule is defined on a different table in the Model, the column's values can still appear in suggestions even though the user cannot query them.#

#We recommend setting model columns with sensitive data to *Secure suggestions*.#

#A model column's *Suggestion settings* and the index on its underlying table column are two separate controls:#

* #The *index* on the table column determines which values ThoughtSpot pre-indexes and can offer as suggestions.#
* #The *Suggestion settings* on the model column determine whether those values are filtered for each user at query time.#

#If the table column's index is already secured by a row-level security rule defined on that same table, the model column does not need *Secure suggestions*. You need *Secure suggestions* when the row-level security rule is defined on a different table that is joined to the source table. For the full set of conditions and a worked example, see <<when-to-use,When to use Secure suggestions>>.#

#Setting a model column to *Secure suggestions* does not disable typeahead suggestions in *Search Data*. ThoughtSpot continues to show suggestions, filtered to the rows each user is permitted to query.#

=== Prerequisites

For secure suggestions to work, the following conditions must be met:

* Strict row-level security must be enabled for the instance.
* Secure suggestions must be enabled for the instance.
* #Row-level security must be applied to the underlying table. Row-level security rules are defined on tables, not on Models.#
* #The model column must be set to *Secure suggestions* in the *Suggestion settings* column, rather than *Inherit table settings* or *Don't show suggestions*.#

#For Spotter suggestion matching (`SECURE_MATCH`), the following additional condition applies:#

* #The underlying table column's index type must be set to *Default*. This applies only to `SECURE_MATCH`. Sample values (`SECURE_SAMPLING`) do not require the underlying table column to be indexed, and continue to flow to Spotter and to column knowledge cards.#


=== Suggestion settings

To change the suggestion settings for a #model column#, follow these steps:

. Open the Model you plan to modify, and make sure you are on the *Columns* tab.

. Scroll across the column settings until you reach *Suggestion settings*.

. For the desired #model column#, select *Secure suggestions* from the drop-down.

. Click *Save changes*.


[#when-to-use]
=== #When to use Secure suggestions#

A model column requires *Secure suggestions* when *all* of the following are true:

* The source table has an RLS rule applied to it, *or* the model column is sourced from a table joined to a table with an RLS rule.
* The model column is indexed for typeahead or Spotter value suggestions.
* The column values must be filtered per user. A user must not see suggestion values from rows they are not permitted to query.

If none of these conditions apply, enabling *Secure suggestions* on a model column adds `SECURE_SAMPLING` query load without any security benefit.

.Example: When a JOIN makes Secure suggestions necessary
[%collapsible]
====
Consider a model built from two Snowflake tables:

* `ORDERS`: contains order details. An RLS rule restricts each user to their own region's orders.
* `PRODUCTS`: a global lookup table of product names. No RLS rule is applied to `PRODUCTS`.

The model joins `ORDERS` to `PRODUCTS`.

*Scenario 1: Secure suggestions needed*
A model column sourcing `PRODUCTS.product_name` is indexed for Spotter suggestions. Even though `PRODUCTS` itself has no RLS rule, the rows visible through the join are already scoped by the `ORDERS` RLS rule. Without *Secure suggestions*, Spotter could surface product names from orders the user cannot see. In this case, enable *Secure suggestions* on this model column.

*Scenario 2: Secure suggestions not needed*
A model column sourcing `PRODUCTS.product_category` is a global classification (for example, "Electronics", "Clothing"). Every user sees the same categories regardless of their RLS context. Enabling *Secure suggestions* here generates unnecessary `SECURE_SAMPLING` queries. Set this model column's suggestion type to *Inherit table settings* or *Don't show suggestions* instead.

[NOTE]
====
*Inherit table settings* inherits the suggestion security setting from the source table and applies it everywhere, not only in typeahead or knowledge cards.
====
====

If the volume of `SECURE_SAMPLING` queries is higher than expected, audit each model column configured with *Secure suggestions*. If the source table has no RLS rule and is not joined to a table with an RLS rule, set the model column's suggestion type to *Inherit table settings* or *Don't show suggestions* to eliminate the unnecessary `SECURE_SAMPLING` load.

[#secondary-warehouse]
== #Secondary warehouse and secure suggestions#

#ThoughtSpot supports routing background indexing queries (`SAGE_INDEXING`, `ROW_COUNT_STATS`) to a secondary warehouse using connection configurations. Secure suggestions queries (`SECURE_SAMPLING`, `SECURE_MATCH_VALUES`) are *not* eligible for this routing.#

#Secure suggestions queries must return quickly to keep search responsive. Secondary warehouses are typically sized and scheduled to run background work during specific time windows to reduce warehouse cost, so routing secure suggestions queries there would make suggestion latency unpredictable. For this reason, the secondary warehouse configuration does not apply to `SECURE_SAMPLING` or `SECURE_MATCH_VALUES`.#

#Because these queries always run on your primary warehouse, they consume compute on that warehouse rather than on a smaller, lower-cost one. On Models where many model columns are set to *Secure suggestions*, this can be a noticeable share of warehouse usage.#
