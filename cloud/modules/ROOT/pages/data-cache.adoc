= Data Cache
:experimental:
:page-last_updated: Nov 4, 2026
:author: Mary
:linkattrs:
:description: Data cache
:jira: SCAL-316578

Data Cache copies frequently queried data from your cloud data warehouse (CDW) into
ThoughtSpot-managed storage, so eligible queries are served from the cache instead of
running on your warehouse. This means faster answers and lower warehouse compute costs.
ThoughtSpot routes a query to the cache when the cache can answer it, and runs it on
your live warehouse when it cannot. Users always get a complete result either way.
Once Data Cache is enabled for your cluster, data model editors can turn on caching
for individual Models from the *Caching* tab in the Model editor. No changes to your
Liveboards, Answers, SQL, or TML are required.

[NOTE]
====
To enable it for your cluster, contact {support-url}.
====

== How it works

When you enable caching on a Model, ThoughtSpot copies the Model's table data into
ThoughtSpot-managed storage on a schedule you choose.
Each eligible query is then evaluated at query time:

* If the cache can answer the query, for example its date filters fall within the
cached window, and the cache is healthy, ThoughtSpot serves the result from the
cache, typically with sub-second latency.
* If the query reaches outside the cached window, uses a construct the cache does not
support, or the cache is unavailable, ThoughtSpot runs the query on your live
warehouse.

Routing is automatic. Users do not choose between the cache and the warehouse, and the
result is complete in both cases. The *Caching* tab shows the current state of the
cache, and View history shows when each refresh ran.

== Prerequisites

Before you can enable caching on a Model, the following must be true:

* Data Cache is enabled for your cluster. Contact {support-url} to enable it.
* The Model is built on a Snowflake or Databricks connection. More sources are being
progressively added.
* The connection uses a service account (non-OAuth, non-parameterized).
* The Model does not use a custom calendar.
* You have edit access to the Model. Users without edit access can open the *Caching*
tab and view the cache settings, but cannot change them.

////
[NOTE]
====
Models that do not meet these prerequisites are not eligible for caching.
ThoughtSpot shows you the reason in the *Caching* tab before you enable it.
====
////

== Enable caching on a Model

. Open the Model editor from the *Data workspace*.
. Select the *Caching* tab.
+
If the Model is not cached yet, the tab describes the benefits of caching and shows
*Cache model*. If Data Cache is not yet enabled for your cluster, *Cache model* is
disabled and the tab asks you to contact {support-url}.
. Click *Cache model*.
+
The *Caching Settings* dialog opens.
. Under *Tables to cache*, choose how to cache each table in the Model:
+
** *Full copy (All history)* — ThoughtSpot copies the entire table into the cache.
Use this for dimension tables or tables where you need the full history available.
** *Date window (Time window)* — ThoughtSpot copies a rolling window of rows,
filtered by a date column you select. The default window is 13 months. You can
adjust the window to any of the following: 1 month, 3 months, 6 months, 13 months,
or a custom duration.
+
A Model may mix full-copy and date-windowed tables. For example, you can cache a large
fact table with a 13-month window and full-copy smaller dimension tables.

. Under *Refresh schedule*, choose how often ThoughtSpot refreshes the cache:
+
** *Frequency*: Hourly, Daily, Weekly, or Monthly.
** *Time and timezone*: Set the time the refresh runs.
+
You can also trigger a manual refresh at any time.
. Click *Save*.
+
The *Caching* tab switches to the cache settings view and shows the *Configuring*
state while ThoughtSpot sets up the cache and loads the data for the first time.

== Cache states

The *Caching* tab shows the current state of the cache for the Model.

[cols="1,2",options="header"]
|===
|State |Meaning

|Configuring
|ThoughtSpot is setting up the cache for this Model. Queries run on your warehouse.

|Caching
|First data load is running. Queries run on your warehouse.

|Active
|Cache is loaded and serving queries.

|Refreshing
|A scheduled or manual refresh is running. The cache continues to serve queries from
the most recent successful load.

|Failed
|The most recent refresh failed. Queries run on your warehouse. Open View history to
see the failed refresh and its per-table detail.

|Purged
|Cached data has been deleted. Queries run on your warehouse. The caching
configuration is kept, so you can cache the Model again without re-configuring.
|===

== Editing a cached Model

Cached Models can't be edited unless caching is turned off. Turning caching off
clears the cached data and run history, so plan your changes before you turn caching
on.

== Refresh the cache manually

. Open the *Caching* tab in the Model editor.
. Click *Refresh now*.

ThoughtSpot starts a new load immediately. The previous cache continues to serve
queries while the refresh runs. A manual refresh reloads all cached tables in full.

////
[NOTE]
====
A manual refresh always performs a full overwrite of all cached tables.
There is no incremental or partial refresh in this release.
====
////

== View refresh history

. Open the *Caching* tab in the Model editor.
. Click *View history*.

The run history shows each refresh: its type (scheduled or manual), start and end
time, number of rows loaded, and whether it succeeded or failed. Click a row to see
per-table detail.

== Purge cached data

Purging deletes all data from the cache immediately. ThoughtSpot returns to serving
all queries from your live warehouse. The caching configuration is preserved — you
can re-enable without re-configuring.

. Open the *Caching* tab in the Model editor.
. Click *Purge data*.
. Confirm the action.

== Disable caching

Disabling caching deletes all cached data and removes the caching configuration from
the Model. This action cannot be undone.

. Open the *Caching* tab in the Model editor.
. Click *Disable caching*.
. Confirm the action.

////
== Freshness indicator

When a query is served from the cache, ThoughtSpot displays a *data as of* timestamp
alongside the result. This shows the watermark time of the most recent successful
refresh.

Queries served from the live warehouse do not show a timestamp.

If the cache data is approaching the staleness limit configured for your cluster,
ThoughtSpot displays a *newer data available* notice. You can dismiss it or trigger
a manual refresh.
////

== Security

Data Cache preserves all existing ThoughtSpot security controls:

* *Row-level security (RLS)* — RLS rules are applied to cached results exactly as
they are to live warehouse results.
* *Column-level security (CLS)* — CLS rules are applied to cached results in the
same way.
* *Org isolation* — Each Org's cache is stored in a separate, isolated database. No
cached data or credentials are shared across Orgs.
* *Encryption* — Cached data is encrypted at rest. Credentials for accessing the
cache are encrypted and stored per Org.
* *Opt-in* — Caching is a double opt-in: your cluster administrator must enable Data
Cache for the cluster, and a data model editor must enable it for each individual
Model. When you enable caching on a Model, ThoughtSpot reminds you that the Model's
data is copied out of your CDW into ThoughtSpot-managed storage.

== Current limitations

Data Cache has the following limitations in this release. When the cache can't serve
a Model or a query, ThoughtSpot runs it on your warehouse automatically, and the
result is the same either way.

[cols="1,2",options="header"]
|===
|Limitation |Details

|Data sources
|Data Cache supports Snowflake connections only. More sources are being added.

|Authentication
|OAuth and parameterized connections aren't supported. The connection must use a
service account or key pair authentication. PrivateLink isn't supported yet.

|On-premise clusters
|Data Cache is available on SaaS clusters only.

|Custom calendars
|Models that use a custom calendar can't be cached.

|SQL views
|Models built on a table that is a SQL view can't be cached.

|SQL passthrough functions
|Models that use a SQL passthrough function in a column, formula, filter, or RLS rule
can't be cached. On a cached Model, queries that use passthrough functions run on your
warehouse.

|Parameters
|Models that use a parameter in a formula, filter, or RLS rule can't be cached. A
parameter that is defined on the Model but not used is fine, and so are system
variables such as ts_username.

|Row-level security
|Models whose RLS rules reference another table, or use a formula or a join, can't be
cached.

|Published Models
|Models published to other Orgs can't be cached. To publish a cached Model, turn
caching off first.

|Time window
|If a table is cached for a time window, queries for dates outside that window run on
your warehouse.

|System queries
|System models don't use the cache. They run on your warehouse.

|Refresh
|Refresh schedules are daily, weekly, or monthly. Each refresh reloads the Model, or
the time window you set for a table. Model changes, such as new or unhidden columns,
appear in the cache at the next refresh.

|Storage
|A full Model cache copies all tables and all columns entirely, so a practical size
ceiling applies per Org. For large tables, set a time window. Contact your ThoughtSpot
representative if you approach storage limits.

|Cluster restore
|Cached data isn't included in cluster snapshots. After a cluster restore, set up
caching again.

|TML
|Cache settings aren't part of a Model's TML. After you import a Model, turn caching
on for it.
|===

== Data Cache and aggregate-aware Models

If a Model has both an xref:model-aggregate-aware.adoc[aggregate-aware configuration]
and Data Cache enabled, ThoughtSpot checks the cache first. Queries the cache cannot
serve run on your warehouse, where aggregate-aware routing applies as usual. You can
use both together: caching reduces the load on your warehouse, and aggregate awareness
speeds up the queries that still run there.

== Data that works best with caching

For the most consistent results between cached and live answers, review the following.

[cols="1,2,3",options="header"]
|===
|Where |What to note |Tip

|`to_integer()` on non-numeric text
|Not supported on cached Models, for example `to_integer('abc')`.
|

|Case-insensitive text columns (Snowflake COLLATE 'en-ci')
|Cached answers treat text as case-sensitive, so 'abc' and 'ABC' show as separate
values.
|Store values in one case at the source, or keep these Models live.

|Decimal values
|Values that differ only after the 15th significant digit are stored as one value.
|Round at the source if you need finer precision.

|VARIANT / ARRAY columns
|Stored as compact JSON, so text filters and grouping on the raw column can differ
from live.
|Extract the fields you need as typed columns.

|Log of zero
|ln(0), log2(0), and log10(0) return 0.
|Use if([Value] = 0, null, ln([Value])) for the same result cached and live.

|Infinity in DOUBLE columns
|Answers that read these rows return an error.
|Replace with NULL or a large number at the source.

|Dates in year 0001
|The yearly bucket shows as null. The raw date is fine.
|Group by the raw date.

|`edit_distance()`
|Not supported on cached Models yet.
|Use a live Model for answers that need it.
|===
