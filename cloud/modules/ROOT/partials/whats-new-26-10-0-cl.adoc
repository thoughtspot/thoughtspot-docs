=== Publish/unpublish in list view [.badge.badge-ga-relnotes]#GA#
Publishing in list views is now generally available (GA). You can now publish, unpublish, and manage the publishing state of Answers, Liveboards, and Models directly from the list page view without having to open each object individually.

The *Publish*, *Unpublish*, and *Manage publishing* options are available in the row-level action menu on the Answers, Liveboards, and Data Workspace list pages. The publish and unpublish options allow you to select target Orgs, handle dependents, and confirm the action.

[#26-10-0-cl-filtering]
[discrete]
=== Liveboard contextual filtering [.badge.badge-early-access-whats-new]#Early Access#
endif::[]
Liveboard creators can now scope filters and parameters to a specific tab or group, instead of applying them globally across the entire Liveboard. This makes it easier to build focused, information-dense Liveboards where consumers can analyze a specific area without inadvertently affecting unrelated visualization. To enable this feature, contact your administrator.

NOTE: When a Liveboard with tab or group filters is imported into a cluster where this feature is disabled, the scoped filters are removed on import.

For more information, see xref:liveboard-filters.adoc[Liveboard filters].
////
*Filter hierarchy*
Filters in a Liveboard now have three levels of scope:

* *Liveboard filters* — The default. Apply across all tabs and
visualizations in the Liveboard, just as before.
* *Tab filters* — Apply only to the visualizations within a specific tab.
The same filter column can be added independently to multiple tabs;
each instance has its own default values, display name, and chip ordering.
* *Group filters* — Apply only to the visualizations within a specific
group inside a tab. Group filters appear contextually within the group,
not in the top-level filter bar.

NOTE: A filter scoped to a tab or group is not visible in tabs or groups
where it does not apply.

*For Liveboard creators*
When adding a filter, a new *Scope* selector lets you choose whether the
filter applies at the Liveboard, tab, or group level. The worksheet
selection is automatically constrained to columns used by visualizations
within the selected scope.

You can also convert an existing filter between scopes using the *Convert
to Liveboard filter* or *Convert to tab filter* option in the filter menu.

Deleting a tab removes all filters scoped to that tab. Deleting a group
removes all filters scoped to that group.

*For Liveboard consumers*
Filters and parameters appear in the context where they are relevant.
Changing a group filter affects only the visualizations in that group;
all other tabs and groups are unaffected.

*For embed developers*
The Visual Embed SDK has been updated to support scoped filtering:

* `FilterChanged` and `ParameterChanged` embed events now include scope
information (Liveboard, tab, or group level) in the event payload.
* `UpdateFilters` and `UpdateParameters` host events accept an optional
`applicability` property per filter or parameter to target a specific
tab or group. Omitting `applicability` defaults to the Liveboard level
and is backward compatible.
* `GetFilters` and `GetParameters` responses now include scope information.
////

  Databricks semantics without hand-building a data model.

[#26-10-0-cl-rls]
[discrete]
=== Row-level security - secure suggestions saved filter values [.badge.badge-beta-whats-new]#Beta#
endif::[]
ThoughtSpot now enforces Row Level Security (RLS) on saved filter values in Answers and Liveboards. When a filter chip displays values from a column marked as *Secure Suggestions* in the data model, ThoughtSpot checks whether the current user has RLS access to those values before displaying them.

NOTE: When filter values are cleared due to RLS enforcement, the user still sees data, but only the rows their RLS policy permits. An empty
filter chip on a secured column does not mean *no data*; it means the saved filter values were not applicable to this user and the RLS policy
is the active constraint.

To enable this feature, contact {support-url}. For more information on Secure Suggestions and RLS, see xref:rls-secure-suggestions.adoc[Row Level Security: Secure Suggestions].

////
Previously, saved filter values were displayed as saved — even if the
user opening the Answer or Liveboard did not have RLS access to all of
those values. This could expose restricted column values in the filter
chip and search bar UI, even though the underlying query results were
already protected by RLS.

With this feature enabled, ThoughtSpot performs an RLS check on the saved
filter values when the Answer or Liveboard is opened:

* If the user has access to *all* saved filter values, the filter chip
displays normally — no change in behavior.
* If the user does *not* have access to one or more saved filter values,
the inaccessible values are removed from the filter chip and search bar.
The filter is applied using only the values the user can access. If none
of the saved values are accessible, the filter chip is cleared and only
the RLS policy on the underlying data governs what the user sees.


*Restricted actions*

To prevent data leakage through exports or object copies, the following
actions are blocked when a user does not have access to all filter values
on a secured column:

* *TML View* and *TML Download* — on the Answer and in the Data
Workspace
* *Extract Data* / *Download* — the filter set is included in the
download; this is blocked to prevent exposing inaccessible values
* *Liveboard Schedule* — scheduled delivery is blocked if the recipient
does not have access to all filter values

*Applies to*

This behavior applies to columns with the *Secure Suggestions* suggestion
setting in the data model. Columns using the default suggestion setting
are not affected.

NOTE: This feature is in Beta and is disabled by default. It must be
enabled by a ThoughtSpot administrator using the following tscli command:
