== What this connector surfaces

⚠️ Confirm the full tool list. Typical tools:

* *Repos* — list, get metadata, list branches, list contents at path, get file content.
* *Code search* — search code across allowed repos with filters (path, language, owner).
* *Pull requests* — list, get, list files in PR, list/post review comments, request review, merge (gated).
* *Issues* — list, get, create, comment, label, close.
* *Commits* — list, get, get diff.
* *Workflows / Actions* — list workflow runs, get logs (optional, scope-dependent).

== Authentication

[cols="1,2",options="header"]
|===
|Pattern |When to use

|*GitHub App (recommended)*
|Install a GitHub App into the org / selected repos. Granular per-repo permissions, predictable identity, easy revocation.

|*OAuth — user pass-through*
|Each user grants consent. Actions show as the user. Good for code review workflows where authorship matters.

|*Personal access token (PAT)*
|Simple; tied to one human's account. Avoid for shared/agent automation — it breaks when that person leaves.
|===

⚠️ Confirm preferred pattern for your tenant.

== Setup (admin)

. Open *Admin* > *Connectors* > *Add connector* > *GitHub*. ⚠️ Confirm path.
. Choose the auth pattern.
. For GitHub App: install the app from the marketplace into your org; pick *All repositories* or specific ones; copy the resulting app ID and private key into AgentSpot.
. For OAuth: complete the OAuth flow with an org-admin GitHub account.
. Review and approve scopes.
. Choose which groups can use the connector.
. (Optional) Restrict by repository — e.g. allow `org/docs` and `org/internal-tools` only.
. Test the connection (list repos).

*Expected result:* Status *Connected*; allowed groups see GitHub tools in builders, scoped to the approved repos.

== Scopes and permissions

⚠️ Confirm exact scopes. Typical GitHub App permissions to request:

* *Repository contents* — read (and write for agents that update files).
* *Pull requests* — read/write.
* *Issues* — read/write.
* *Metadata* — read (always required).
* *Actions* — read (only if agents need workflow logs).
* *Members* — read (only if agents reason about who's in the org).

Best practice:

* Start with read-only on all permissions; add write per-permission only when a use case justifies it.
* Use repository-scoped install over org-wide install when possible.
* For write actions, prefer a workflow with a *Wait for approval* step over a direct agent call.

== Common patterns

* *Code Q&A* — agent answers questions about a codebase by searching code and reading files; cites file paths and line numbers.
* *PR review assistant* — workflow triggered on `pull_request.opened`; agent reviews the diff, posts comments on risky changes, requests a human reviewer.
* *Issue triage* — workflow on `issues.opened`; agent assigns labels, suggests owner, posts a clarifying comment if the issue is underspecified.
* *Release-notes drafter* — workflow runs weekly; gathers merged PRs since last tag, an agent drafts release notes grouped by feature/fix/breaking, posts to a Doc for review.
* *Docs synchroniser* — when a PR merges that changes public-facing behaviour, the agent opens an issue against the docs repo with suggested updates.

== Limits

⚠️ Confirm specific quotas with [feature owner] and GitHub's API documentation. Watch for:

* GitHub REST API rate limits (per-app or per-user, per hour).
* GraphQL point-cost limits (some queries are cheap, some are expensive).
* Pagination — list calls cap at 100 items per page; agents must paginate or filter.
* Search API has its own (lower) rate limit; don't call it in a tight loop.

== Privacy and code exposure

* Code content sent to the underlying model is governed by your model provider's data-handling terms. Confirm with your provider before enabling code-search use cases on private repos.
* Restrict the connector to repos that are safe to expose to your model provider — exclude any repo containing secrets, customer data, or compliance-sensitive code.
* Agents that *write* to GitHub leave an audit trail under their identity (GitHub App or user). Make sure that identity is named clearly so reviewers know what they're looking at.

== Troubleshooting

[cols="1,2",options="header"]
|===
|Symptom |What to try

|"Not Found" on a repo you know exists.
|GitHub App not installed on that repo, or PAT lacks access. Add the repo to the app installation.

|Code search returns no results.
|Confirm the repos are indexed by GitHub's code search (some forks and private repos require explicit enablement).

|Rate-limit (429) errors in workflows.
|Add retry-with-backoff on the connector step; reduce poll frequency on event triggers.

|PR comment posts but appears as the wrong user.
|GitHub App posts under the app's bot user, not the human's. For user attribution, switch to user pass-through OAuth.

|Agent reads a file but content looks truncated.
|Files over GitHub's API size limit (1 MB raw) need to be fetched via the git blob endpoint, not the contents endpoint.
|===
