== Identity and authentication

* *Sign-in path:* AgentSpot has no separate password store. All authentication flows through your ThoughtSpot tenant's configured SSO (SAML 2.0 or OIDC). Disabling the user in your IdP revokes AgentSpot access at the next sign-in.
* *Service-to-service auth* (e.g. to connectors and model providers) uses per-connection credentials stored encrypted at rest. Credentials are never returned through the API once written.
* *Session tokens* are short-lived and refresh according to your tenant's session policy. ⚠️ Confirm default session length.
* *MFA* is enforced upstream by your IdP — AgentSpot trusts the IdP's MFA decision.

== Authorisation model

Three layers:

. *Roles* — coarse-grained capability (admin, builder, consumer, auditor). See xref:02-authentication-and-access.adoc[Authentication and access].
. *Groups* — fine-grained visibility (which agents, workflows, connectors, data sources each user can see).
. *Per-resource sharing* — at publish time, agents and workflows are restricted to specific groups. Connectors and data sources are restricted to specific groups by the admin.

The intersection determines what a user can do: they must hold the right *role* AND be in the right *group* AND the *resource* must be shared with their group.

== Tenant isolation

* *Logical isolation:* each tenant's data, configuration, and audit logs are partitioned by tenant ID. Inter-tenant access is impossible through the API.
* *Memory isolation:* memory is partitioned by scope (user, user+agent, agent, tenant). Cross-tenant memory access is impossible.
* *Connector isolation:* connector credentials are tenant-scoped. One tenant's credentials are never visible to another tenant.
* *Audit isolation:* one tenant's audit log is invisible to another.

⚠️ Confirm physical isolation model (shared vs dedicated infrastructure per tenant) with [feature owner].

== Encryption

* *In transit:* all traffic between user → AgentSpot, AgentSpot → connectors, AgentSpot → model providers is TLS 1.2+. ⚠️ Confirm minimum TLS version.
* *At rest:* connector credentials, model-provider keys, conversation content, files, and memory are encrypted with a tenant-scoped key. ⚠️ Confirm key-management model (KMS, BYOK).
* *Backup:* backup data is encrypted with the same standard as production data. ⚠️ Confirm backup retention and restore SLAs.

== Data flow

A typical agent run touches four systems:

. *User browser* sends the user's message to AgentSpot.
. *AgentSpot* assembles context (instructions, attached data, memory, prior session messages) and dispatches to the model provider.
. *Model provider* returns a response, possibly including tool-call requests.
. *Connectors* execute tool calls against external systems and return results to AgentSpot.

Data sent to each external system is governed by that system's data-handling terms:

* *Model provider data handling* — confirm with each provider whether your data is used for training. The default for most enterprise tiers is "no training." Document the answer per provider for your security review.
* *Connector destination data handling* — connectors send data to the destination system per its standard model (e.g. Slack stores your messages, Salesforce stores your queries).

⚠️ Confirm exact data-flow diagrams and provider-by-provider data-handling posture with [feature owner].

== Network posture

* *Inbound:* AgentSpot is reachable on standard HTTPS ports from end-user browsers.
* *Outbound:* AgentSpot makes outbound HTTPS calls to model providers, configured connectors, and (if enabled) the allow-listed domains for web egress.
* *IP allow-listing:* if your downstream systems require AgentSpot calls to come from a known IP range, your tenant has a documented set. ⚠️ Confirm IP ranges.
* *Private connectivity:* private-link / VPC-peering options for connecting to customer-managed data sources. ⚠️ Confirm availability per region and edition.

== Custom MCP security

Custom MCP servers are customer-managed — your code, your hosting, your downstream credentials.

AgentSpot enforces:

* HTTPS-only transport.
* Per-connection authentication between AgentSpot and your MCP server (bearer token, mTLS, etc.).
* Admin approval of the MCP server's tool manifest before agents can use it.

You enforce:

* Authentication to *your* downstream systems.
* Tool-level rate limits and audit on your side.
* Server availability and patch posture.

See xref:../03-connectors/07-custom-mcp.adoc[Custom MCP].

== Audit and observability

* *Every meaningful action is auditable* — sign-ins, agent and workflow lifecycle events, executions, tool calls, configuration changes, memory operations, guardrail triggers, quota exhaustion, admin actions.
* *Audit retention* is configurable per tenant. ⚠️ Confirm default and maximum.
* *Audit export* pushes events to your SIEM (Splunk, Datadog, S3) on a near-real-time cadence. ⚠️ Confirm exact latency.
* *Audit immutability* — audit records cannot be edited or deleted by admins; they can only age out per retention policy. ⚠️ Confirm immutability guarantee.

For configuration, see xref:04-usage-and-limits.adoc#audit-logging[Audit logging].

== Guardrails and content controls

* *Tenant-level guardrails* block categories of content (PII, regulated advice, prompt-injection attempts). Tenant defaults are enforced; specific agents can be stricter but not laxer.
* *Egress allow-list* restricts where agents can send outbound calls.
* *Prompt-injection defences* — the platform treats untrusted content (tool output, uploaded files, retrieved documents) as data, not instructions. Agents are configured to ignore embedded "system prompts" inside user uploads.

⚠️ Confirm the specific guardrail categories and prompt-injection model with [feature owner].

== Compliance posture

⚠️ Confirm current certifications with [feature owner]. Typical posture for an enterprise ThoughtSpot tenant:

* SOC 2 Type II.
* ISO 27001.
* GDPR processing terms.
* HIPAA — for editions where applicable.
* Regional data-residency commitments — per supported region.

Compliance attestations and data processing agreements are available through your ThoughtSpot account team.

== Incident response

* *Detection:* AgentSpot operates continuous monitoring on tenant-level signals (auth anomalies, quota breaches, unusual tool patterns).
* *Notification:* incidents affecting your tenant are communicated per the ThoughtSpot incident-response policy you signed with your subscription. ⚠️ Confirm SLAs.
* *Customer-initiated:* if you suspect a security incident in your tenant, contact ThoughtSpot Support with severity *Critical*. Provide the audit-event range and any evidence available.

== What you control vs what ThoughtSpot controls

[cols="1,1",options="header"]
|===
|You control |ThoughtSpot controls

|IdP, SSO, MFA, user lifecycle
|Tenant infrastructure, isolation, encryption keys (per BYOK posture)

|Connector credentials and scope
|Connector availability and platform security

|Model provider choice and data-handling acceptance
|Model invocation, response handling, audit

|Group structure and per-resource sharing
|Role enforcement, authorisation checks

|Guardrail and quota settings within tenant defaults
|Tenant default ranges, platform-level guardrails

|Custom MCP servers and their downstream auth
|Custom-MCP transport and approval enforcement

|Audit destination (your SIEM)
|Audit collection, immutability, export reliability
|===

== Security-review checklist

For your internal security review of AgentSpot adoption:

* [ ] SSO connected; IdP MFA enforced; role mapping reviewed.
* [ ] Per-provider data-handling terms documented.
* [ ] Connector scopes minimised; read-first posture for the first month.
* [ ] Guardrails enabled for relevant content categories.
* [ ] Egress allow-list configured.
* [ ] Audit export to SIEM working; retention set to your policy.
* [ ] Incident-response contact path documented internally.
* [ ] Custom-MCP servers (if any) reviewed against the xref:../03-connectors/07-custom-mcp.adoc#security-checklist[security checklist].
* [ ] Quotas set to detect runaway behaviour without throttling normal use.
* [ ] Pilot users completed; documented learnings.
