= Design Patterns
:doctype: book

:icons: font

[.lead]
Reusable shapes for agents and workflows. Each pattern names the problem it solves, the structure, when to use it, and when to avoid it.

== Agent patterns

=== The narrow Q&A agent

*Problem:* A team keeps asking the same kinds of questions over the same data.

*Structure:*

* Two or three carefully scoped data sources (often ThoughtSpot Worksheets).
* Instructions with explicit *Authority* (what's in scope, what's not) and *Anchors* (fallback when uncertain).
* No skills.
* Citations on.
* Low temperature.

*Use when:* the questions are answerable from your data, the scope is well understood, and the answer should be consistent across users.

*Avoid when:* every question is one-off, the data changes shape weekly, or the value is in the conversation rather than the answer.

=== The drafter

*Problem:* Someone produces a recurring artifact (email reply, ticket response, summary) from a known input.

*Structure:*

* One data source (the input format) plus templates or examples in the prompt.
* Skills: usually none. Output stays in chat; the human edits and sends.
* Instructions with a *Style* section that pins voice, length, and required sections.

*Use when:* the output has a consistent shape and the human is the final editor.

*Avoid when:* you'd be tempted to auto-send. Drafters are draft-only by design.

=== The triage agent

*Problem:* Incoming items (leads, tickets, emails) need quick classification and routing.

*Structure:*

* One data source: the record being triaged plus a small reference table (rules, owners, segments).
* A skill that writes the routing decision back (CRM update, Slack ping, label change).
* Instructions with a *Tactics* section listing the classification steps in order.
* Returns *structured* output: `{ class: ..., reason: ..., next_owner: ... }`.

*Use when:* the routing logic is mostly rule-based with a small judgement-call edge.

*Avoid when:* the routing decision needs human judgement on every case. Use a *drafter* that suggests, not a triage agent that decides.

=== The researcher

*Problem:* The user has an open-ended question that requires gathering, comparing, and synthesizing across sources.

*Structure:*

* Multiple data sources plus a web-search skill.
* Instructions with a strong *Tactics* section: "search the connected data first; only use the web if internal data is insufficient; always cite."
* Higher response-length cap; the answer will be longer.
* Citations on, always.

*Use when:* the user is doing genuine exploration and the value is in the synthesis.

*Avoid when:* there's a known answer in a known place. Use the *narrow Q&A* agent.

== Workflow patterns

These map to the four examples in xref:../02-workflows/04-example-patterns.adoc[Example patterns]. Reread that article for the per-pattern step diagrams. The notes below are the design considerations behind picking each pattern.

=== Scheduled digest

* Pick when: the same summary needs to land in the same place at the same time.
* Single source of truth: the workflow's *Schedule* trigger. Don't also have someone running it manually.
* Always include the as-of timestamp in the output so consumers don't compare yesterday's digest with today's data.

=== Inbound triage

* Pick when: events arrive faster than humans can hand-classify them.
* Always set a concurrency cap on the trigger; bursty event sources can spawn many parallel runs.
* The classification agent should return *structured* output, not free text, so the *Branch* step can route deterministically.
* Always include a "needs human triage" fallback branch for malformed inputs or low-confidence classifications.

=== Multi-step research and draft

* Pick when: a deliverable depends on data from multiple systems, the output is a document, and a human will review.
* Use parallel *Fetch data* steps where possible — they cut total runtime.
* Include the source for each section in the output, so the reviewer can spot-check.
* For weekly cadence, append to a rolling doc; for monthly cadence, create a new doc per period.

=== Human-in-the-loop approval

* Pick when: the workflow takes an action with real-world consequences (money, customer-facing message, irreversible write).
* Use *Wait for approval* with a generous timeout (48 hours business time) and escalation.
* Never auto-approve on timeout for financial or compliance flows.
* Capture the approver's identity and decision time in the audit trail — this is the whole point of the pattern.

== Cross-cutting patterns

=== Promote in stages

For both agents and workflows: *Private* → *Group* → *Organization*. Each step is a cheap chance to catch problems.

Concretely:

* *Private (week 1):* you're the only user. Iterate fast. Failures are invisible.
* *Group (weeks 2–3):* small audience. Failures are visible to a few people who care. Collect feedback.
* *Organization (week 4+):* wider audience. Failures are visible to many. Don't promote anything that hasn't survived the group phase clean.

=== Idempotent writes

When a workflow writes to an external system, design the write to be safe to repeat. Use upserts keyed on a stable id rather than blind creates. This way, retrying a failed run doesn't double-create anything.

=== Approval-then-remove

Add a *Wait for approval* step in front of any irreversible external action while building trust. Remove it after two weeks of clean runs. This is faster than building bulletproof first-time logic.

=== Structured outputs across step boundaries

Wherever a step's output feeds the next step's input, prefer structured (`{ field: ... }`) over free text. Structured outputs make downstream references explicit, brittle in good ways (you see the failure), and easy to audit.

=== Observability before automation

Wire failure alerts before activating the trigger. A workflow that runs without observability builds up silent failures you don't notice until users complain.

== When to break a pattern

Patterns are starting points, not rules.

* Break the *narrow Q&A* shape when a use case genuinely needs cross-cutting reasoning (and use *researcher* instead).
* Break the *promote in stages* rhythm when you're replacing an obviously broken existing agent — go straight to the same audience the broken one had.
* Break *human-in-the-loop* once the workflow has run cleanly long enough that the approval step is purely ceremonial.

The mark of breaking a pattern well: you can explain why in one sentence to your successor.
